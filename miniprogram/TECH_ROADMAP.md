## 一、文档目的

回答三个问题:

1. **要新增哪些功能?** —— 从业务流程的每个环节倒推,而不是凭感觉堆功能。
2. **为什么是这些?** —— 每个功能必须对应业务流程中一个真实存在的断点。
3. **为什么这么排优先级?** —— 给出可量化、可复盘的决策模型,而不是拍脑袋。

## 二、业务流程建模

用户价值只有在流程中才能被定位。先把组间记的完整用户旅程拆成 **5 个阶段**,后续所有功能都挂载到具体阶段上。

```
┌─────────────────────────────────────────────────────────────────┐
│  A. 首次触达                                                     │
│     扫码 / 好友分享 / 搜索 → 打开小程序 → 首页                    │
│     ⚠️ 当前断点:无分享入口、无渠道归因、无新手引导                  │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  B. 激活(首训转化)                                                │
│     首页空状态 → 点"开始新训练" → 选动作 → 开始设置 → 进入训练     │
│     ⚠️ 当前断点:空状态无引导、无默认推荐动作、首训转化率未知         │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  C. 核心训练(主链路,产品命脉)                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 单组循环(每 60-180s 一轮):                                │   │
│  │   点大按钮 → 记录 Sheet → 微调重量/次数                    │   │
│  │   → 长按 1.5s 确认 → 组数 +1 → 自动进入休息倒计时          │   │
│  │   → 休息结束(震动 + 视觉提示)→ 下一组                      │   │
│  │   ↳ 3 秒内可撤销 ↳ 120 秒无操作触发"漏记提醒"              │   │
│  └─────────────────────────────────────────────────────────┘   │
│     ⚠️ 当前断点:无崩溃兜底、无网络兜底、无异常上报                 │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  D. 完成与成就(留存黄金时刻)                                      │
│     达到目标组数 → 训练完成总结 → 3s 撤销窗口 → 返回训练页         │
│     ⚠️ 当前断点:无成就感放大、无订阅授权、无分享、数据不落云端      │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  E. 回流与传播(增长)                                              │
│     查看今日总结 / 历史记录 → 下次训练 → 分享给好友                │
│     ⚠️ 当前断点:无分享卡片、无订阅召回、换机数据全丢                │
└─────────────────────────────────────────────────────────────────┘
```

### 流程中的 5 个"情绪高点"——功能插入的最佳时机

| 时刻 | 用户心理状态 | 最适合做什么 | 最忌讳做什么 |
|------|-------------|-------------|-------------|
| **首次打开** | 好奇、没耐心 | 一句话价值传达 + 首训引导 | 弹窗授权、复杂引导 |
| **完成一组** | 轻微成就感 | 订阅消息授权(此刻情绪最高) | 打断、广告 |
| **训练完成** | **成就感峰值** | 成就放大 + 总结卡分享 + 订阅 | 立刻要求评价 |
| **休息中(60-300s)** | 无聊、刷手机 | 轻内容(上一组成绩/PR 提示) | 阻断训练节奏的弹窗 |
| **查看记录** | 回顾、有炫耀欲 | 数据可视化 + 分享卡片 | 纯表格罗列 |

> **设计原则**:功能必须挂在"情绪高点"上。在用户力竭时弹订阅授权 = 骚扰;在用户刚破 PR 时弹 = 服务。

## 五、优先级决策模型(核心)

### 5.1 第一性原理

小程序上线后的用户价值可以拆成:

```
用户价值 = 可上线 × 留存率 × 新增用户 × 使用频次 × 单次体验
```

这是一个**乘法关系**,不是加法。任何一项为 0,整体结果为 0。这就决定了优先级不是"哪个功能更酷",而是**"哪个环节是当前最致命的乘数瓶颈"**。

### 5.2 四层漏斗排序法

按"归零风险"从高到低排列,每一层都是下一层的前提:

```
第 1 层:能不能上线?   ← 归零风险最高:上不了线,后面全是 0
   ↓
第 2 层:能不能留人?   ← 工具型产品的生死线:数据丢了,一次都不信你
   ↓
第 3 层:能不能拉人?   ← 留存达标后,增长才有复利
   ↓
第 4 层:能不能更好用? ← 长尾优化,但不解决"有没有人用"
```

### 5.3 为什么"留存"排在"增长"前面(反直觉但关键)

很多人认为"要快速获客"就应该先做分享。这个判断在工具型小程序上是**错误**的,原因有四:

1. **工具无内容消费属性** — 用户不会"逛"一个训练记录工具,使用频次天然低(一周 3-5 次)。拉新后如果没有召回机制,7 日留存必然崩盘。
2. **数据丢失是信任的绝对杀手** — 当前数据全在 `wx.storage`,用户换手机 / 清缓存 / 重装微信 = 训练历史全部归零。一次丢失,永久流失,且会产生负面口碑。
3. **分享是"一次性消耗社交货币"** — 留存差的产品,用户第一次分享后,好友来了也留不住,用户下次就不愿意分享了。分享价值会被低留存反向清零。
4. **有内容的分享 > 无内容的分享** — 训练总结卡是"结果分享"(有具体成绩、有炫耀点),而单纯的小程序入口是"无内容分享"。前者转化率是后者的数倍。而**结果分享的前提是数据可靠**。

> **结论**:`云同步 → 订阅召回 → 总结卡分享` 这个顺序不可颠倒。先把数据托住,再谈传播。

### 5.4 RICE 量化评分

对每个 P0/P1 功能打分,`Score = (Reach × Impact × Confidence) ÷ Effort`。

- **Reach** 覆盖用户比例(1-10)
- **Impact** 单用户影响力(0.25 / 0.5 / 1 / 2 / 3)
- **Confidence** 信心系数(0.5=不确定 / 0.8=较确定 / 1.0=很确定)
- **Effort** 人日投入

| 功能 | Reach | Impact | Conf | Effort | **Score** | 排级 |
|------|:-----:|:------:|:----:|:------:|:---------:|:----:|
| X1 隐私协议 + 用户协议 | 10 | 3 | 1.0 | 0.5 | **60.0** | P0 |

- `C3 组件拆分` / `E4 数据图表` 得分垫底 —— 属于工程治理和长尾体验,**有团队余力再做**,不应阻塞上线。

## 七、技术架构设计

### 7.1 分层架构

```
┌──────────────────────────────────────────────────────┐
│  Pages 层      UI 编排 + 事件转发,不含业务规则          │
├──────────────────────────────────────────────────────┤
│  Components 层 可复用 UI:rest-timer/confirm-button 等  │
├──────────────────────────────────────────────────────┤
│  Services 层   业务编排:auth / sync / share / sub      │
├──────────────────────────────────────────────────────┤
│  Utils 层      纯函数 + 工具:request/storage/session   │
├──────────────────────────────────────────────────────┤
│  Cloud 层      微信云开发:login / record-sync / cron   │
└──────────────────────────────────────────────────────┘
```

**核心约束**:Pages 只做 UI 编排;业务规则在 Services;数据变换在 Utils(纯函数)。

> 这样设计的好处:后期从"微信云开发"迁移到"自建后端"时,**只需替换 `services/sync.js` 一处,Pages 零改动**。

### 7.3 数据模型演进

**本地 `wx.storage`(已有,保持不变)**

| Key | 内容 |
|-----|------|
| `current_session` | 进行中的训练会话 |
| `training_records` | 历史训练记录数组 |
| `rest_duration_seconds` | 休息时长偏好 |
| `custom_exercises` | 自定义动作 |
| `exercise_overrides` | 预设动作个人覆盖值 |

**云端集合(新增)**

```
users
  _id / _openid / createdAt / lastActiveAt
  profile: { nickname, avatarUrl }
  stats:   { totalWorkouts, totalVolume, currentStreak, maxStreak }

records
  _id / _openid / recordId(本地 ID,用于幂等)
  exerciseId / exerciseName / categoryName
  sets[] / totalSets / totalVolume
  startedAt / completedAt / syncedAt

subscriptions
  _id / _openid / templateIds[] / acceptedAt
```

> **幂等设计**:`recordId` 使用本地生成的 `session-${startedAt}`,即使重复上传也不会产生脏数据。这是"本地优先 + 异步同步"能成立的关键。

### 7.4 同步策略:本地优先 + 后台异步

```
用户完成一组
  ↓
① 立即写本地 storage        ← 用户感知延迟 = 0
② 立即更新 UI               ← 不等待网络
③ 后台异步上传云端          ← 失败进 dirty 队列
  ↓
下次启动:pullRecords() 合并本地 + 云端
```

**为什么不做"实时强同步"?**
训练场景可能发生在**健身房地下室、信号差**的环境。如果强依赖网络,一次请求失败就会阻塞记录,直接摧毁"1 次点击完成记录"这个核心价值主张。**本地优先是产品体验的刚性要求,不是技术妥协。**

## 八、微信生态约束与合规

| 约束 | 影响 | 应对 |
|------|------|------|
| **域名白名单** | 所有请求域名须在后台登记 | 用微信云开发可**免域名配置**(默认可信),这也是推荐云开发的原因之一 |
| **主包 ≤ 2MB** | 当前无图片资源,压力小 | Canvas 总结卡在客户端生成,不占用包体 |
| **隐私协议强制** | 2023 年起审核硬性要求 | X1 列为最高优先级 |
| **订阅消息需用户主动触发** | 不能启动即弹 | 挂在"完成训练"按钮(情绪峰值),授权率最高 |
| **分享图 ≤ 128KB / 5:4** | 总结卡尺寸限制 | Canvas 输出后压缩,或用云函数生成后返回 URL |
| **基库版本兼容** | 当前 libVersion 3.7.0 | 订阅消息需 ≥ 2.4.4,云开发需 ≥ 2.2.3,均满足 |

| 风险 | 等级 | 应对 |
|------|:----:|------|

## 附录:关键决策速查

| 问题 | 决策 | 理由 |
|------|------|------|
| 用云开发还是自建后端? | **微信云开发** | 免运维、免备案、免域名白名单,契合"快速上线" |
| 先做分享还是先做云同步? | **先云同步** | 工具型产品,留存放大增长价值;数据丢失不可逆 |
| 训练主流程是否阻塞登录? | **不阻塞** | 静默登录,未登录也能训练,数据暂存本地后续补传 |
| 订阅授权弹在哪? | **完成训练后** | 用户情绪峰值,且符合"主动触发"规则 |
| 强同步还是本地优先? | **本地优先** | 健身房弱网是常态,不能让网络阻塞核心记录动作 |
| 阶段一是否加新功能? | **不加** | 功能已够用,拼的是上线通道,不是功能数量 |

### B.3 上线前必须完成的 5 项微信侧配置

#### 步骤 1:开通云开发,填入环境 ID

编辑 `utils/config.js`,按环境填入 `cloudEnv`:

```js
release: {
  cloudEnv: 'fitsync-prod-xxxxxxxx',  // ← 替换为你自己的环境 ID
  enableLog: false,
  enableAnalytics: true,
  requestTimeout: 8000
}
```

> **未填写时小程序不会报错**,而是自动降级为纯本地模式 —— 训练、记录、统计全部可用,
> 只是数据不上传云端。这正是为了让后端尚未就绪时也能正常开发和体验而设计的。

#### 步骤 2:部署云函数

在微信开发者工具中,右键 `cloud/functions/` 下的每个目录,选择「上传并部署(云端安装依赖)」。

依次部署:`login` → `recordSync` → `dailyRemind`。

#### 步骤 3:创建数据库集合

云开发控制台 → 数据库 → 新建集合,共 4 个:

| 集合名 | 用途 |
|--------|------|
| `users` | 用户档案与汇总统计(streak / 总容量) |
| `records` | 训练记录,`recordId` 建索引可提升同步性能 |
| `subscriptions` | 订阅消息授权额度,由 dailyRemind 消费 |
| `analytics` | 埋点事件流水 |

权限保持默认的「仅创建者可读写」即可,天然满足数据隔离。

#### 步骤 4:申请订阅消息模板

小程序后台 → 订阅消息 → 公共模板库,选用「训练提醒」类模板。

拿到模板 ID 后填入 `services/subscription.js`:

```js
const TEMPLATE_CONFIG = {
  remind: '你的模板ID',
  weekly: ''   // 周报模板,暂未启用可留空
};
```

> 同样地,**未配置模板时不会报错**,授权流程会自动静默跳过。

#### 步骤 5:提交隐私保护指引

小程序后台 → 设置 → 服务内容声明 → **用户隐私保护指引**,填写并提交审核。

⚠️ 注意:后台的隐私指引与小程序内的 `agreement` 页是**两套独立要求**,两者都要做。
只有其中之一通常会导致审核被拒。
